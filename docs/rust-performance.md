# Rust 性能优化路线

## 结论

VideoRecBack 当前最耗时的媒体分析、封面生成和 HLS 转码都由 FFmpeg、ffprobe、Pillow、libwebp 和 SQLite 等原生实现承担。直接把 Python 调度层整体改写为 Rust，不会显著提升转码速度，却会增加构建、跨架构发布和维护成本。

Rust 更适合逐步替换两个边界清晰、能够独立压测的路径：

1. 原画 HTTP Range 串流。
2. 大规模目录快照扫描。

在基准数据证明收益前，不建议重写 FFmpeg 调度、缩略图处理、SQLite 访问或整个 Web 服务。

## 当前热点判断

### 原画串流

`app/media.py` 使用 Python 生成器按 1 MB 分块读取文件，再交给 `StreamingResponse`。单路播放通常受磁盘或网络限制，但多路原画同时播放时，每个分块都会经过 Python 和 ASGI 调度，可能增加 CPU、上下文切换和尾延迟。

这是 Rust 最有可能降低常驻 CPU 的路径。候选实现是一个小型 `axum`/`tokio` 辅助服务，只负责经过授权的只读 Range 响应。Python 仍管理页面、数据库和权限，向 Rust 服务签发短期签名请求。该服务必须限制媒体根目录、拒绝路径穿越，并支持 `HEAD`、单 Range、取消传输和正确的 `416` 响应。

在引入 Rust 前，应先验证当前 Starlette `FileResponse` 或 ASGI `http.response.pathsend` 能否替代自定义生成器。如果现有 Python 栈已经能走操作系统文件发送路径，Rust 的收益可能不足以覆盖复杂度。

### 目录扫描

扫描器已经使用 `os.scandir`，目录枚举本身在 CPython 中由原生系统调用实现；在 SMB、NFS 等 NAS 挂载上，延迟通常来自网络元数据请求，而不是 Python 循环。

当视频数量达到数万或数十万，并且目录位于本地 SSD 或低延迟存储时，可以评估 Rust `videorecback-indexer`：

- 使用迭代式目录遍历收集路径、大小和纳秒时间戳。
- 在 Rust 内完成扩展名、点文件和忽略规则过滤。
- 以有界批次返回紧凑快照，Python 继续负责 SQLite 比较和媒体任务排队。
- 保持符号链接、权限错误、文件扫描期间被删除等语义与现有实现一致。

首选独立二进制加流式协议，便于失败时回退到 Python 扫描器；只有进程通信成为明确瓶颈后，才考虑 PyO3 扩展。

### 不建议优先改写的路径

- FFmpeg/HLS：主要 CPU 时间在编码器内，Rust 只能替换很薄的进程管理层。
- ffprobe：媒体解析由 FFmpeg 库完成，改用 Rust 绑定不会自然获得吞吐提升，还会增加 ABI 和镜像构建风险。
- 缩略图和 WebP：现有 Pillow、FFmpeg、libwebp 已经是原生实现。
- SQLite：当前使用 WAL、批量写入和索引，单用户 NAS 场景通常不是首要瓶颈。
- 全量 Rust Web 重写：迁移成本高，且无法改善磁盘、网络和编码器限制。

## 分阶段实施

### 阶段 0：建立基准

固定同一批媒体和同一挂载方式，记录：

- 1 万、5 万和 10 万文件的首次扫描与未变化复扫耗时。
- 本地 SSD、SMB、NFS 分别测试。
- 1、4、8 路原画播放时的容器 CPU、内存、总吞吐和 P95 响应延迟。
- HLS 首片时间单独记录，避免把 FFmpeg 时间算到 Web 层收益中。

### 阶段 1：低成本 Python 路径优化

- 评估升级后的 Starlette `FileResponse` Range 支持。
- 验证 ASGI 服务器是否支持文件路径发送扩展。
- 对扫描器增加分阶段计时，区分目录枚举、数据库比较、ffprobe 和封面生成。

只有这一步仍无法达到目标，才进入 Rust 原型。

### 阶段 2：Rust 原画串流原型

- 独立、只读、无数据库写入。
- Python 签发包含视频 ID、路径摘要、到期时间和随机数的 HMAC 请求。
- Rust 校验签名和媒体根目录后发送文件。
- 默认关闭，可通过环境变量启用；异常时回退 Python 路由。

建议验收门槛：

- 4 路原画播放时 Python 容器 CPU 降低至少 30%。
- 总吞吐不低于当前实现。
- P95 首字节延迟不增加超过 5%。
- 路径穿越、过期签名和非法 Range 测试全部通过。

### 阶段 3：Rust 扫描器原型

- 保留 Python 扫描器作为兼容回退。
- 使用同一套忽略规则测试夹具比较结果。
- 对本地盘和 NAS 挂载分别判断收益。

建议验收门槛：

- 本地低延迟存储扫描耗时降低至少 25%。
- NAS 挂载复扫耗时降低至少 10%，否则不增加发布复杂度。
- 文件集合、大小、时间戳和错误计数与 Python 实现一致。

## 发布和维护约束

- CI 至少构建 `linux/amd64` 和 `linux/arm64`。
- Rust 二进制版本必须写入应用诊断信息，便于确认实际是否启用。
- Docker 构建使用多阶段编译，不把 Rust 工具链带入运行镜像。
- Rust 辅助进程失败不能影响页面、扫描和播放的 Python 回退路径。
- 每次升级 Rust、FFmpeg 或基础镜像都运行相同基准，避免仅凭语言选择判断性能。
